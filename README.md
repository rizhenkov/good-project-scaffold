# Документация монорепозитория

Готовый набор документов для продукта, у которого api, веб-клиент и фоновые задачи
живут в одном репозитории. Он отвечает на вопросы, которые встают в каждой команде:
куда положить новый код, как оформлять ошибки, как менять схему базы и не потерять
данные, как устроены очереди и тесты, где записывать принятые решения. Один
репозиторий нужен затем, чтобы одно изменение меняло и api, и страницу, которая его
вызывает, а одно решение сразу действовало для всех приложений.

Правила основаны на реальном опыте, а не только на книгах: многие появились после конкретной
ошибки в production, и у многих рядом сказано, от какой ошибки они защищают. Кто знает
DDD или «чистую архитектуру», узнает отдельные приёмы: слои, сущности со своим
поведением, репозитории. Но это не вся методология целиком. Что сознательно не взято
и почему — в [Layer-Boundaries](apps/api/docs/Conventions/Layer-Boundaries.md#чего-здесь-нет).

Документы двух видов. Готовые правила можно брать как есть. Шаблоны помечены в начале
и подсказывают, что написать в каждом разделе. Примеры кода — на TypeScript.

## Как начать

Скопируйте каркас в репозиторий и попросите агента инициализировать документацию. Он
выполнит [scaffold/INIT.md](scaffold/INIT.md): уточнит детали проекта, применит
подходящий [профиль платформы](scaffold/profiles/README.md), удалит лишнее и сам каталог
`scaffold/`. Точка входа для агентов — [AGENTS.md](AGENTS.md).

## Допущения

Каркас рассчитан на такой стек; если допущение не выполняется, затронутые документы
переписываются или удаляются при инициализации.

- Монорепозиторий: api и веб-клиент, при необходимости — воркеры и скрипты.
- TypeScript во всех приложениях.
- api — HTTP JSON API со слоистой архитектурой (domain, application, infrastructure,
  presentation) и сборкой зависимостей в одном composition root.
- Реляционная БД через ORM, у которого единственный источник истины — файл схемы, а
  миграции генерируются; примеры — на Prisma.
- Контракт между клиентом и api — спецификация OpenAPI, собранная из схем валидации.
- Фоновая работа — очередь с доставкой at-least-once и dead-letter, плюс расписания.

Общие правила от платформы не зависят. Всё, что зависит от рантайма, БД и очереди
(время жизни контейнера, транзакции, лимиты, семантика очереди, тестовый рантайм), —
в профиле платформы `apps/api/docs/Platform.md`.

## Где живёт документ

Документ живёт рядом с тем, кто им пользуется:

- **нужен одному приложению** — `apps/<app>/docs/`;
- **нужен нескольким приложениям или описывает продукт целиком** — корневой `docs/`:
  решения (ADR), словарь интерфейса, бэклог, процедуры с юридическим смыслом.

Решения (что выбрали и почему) — только в ADR; живые документы описывают механику и
ссылаются на пункты ADR, а не пересказывают их. Подробно — в
[docs/ADR/README.md](docs/ADR/README.md).

Контракт между приложениями — спецификация OpenAPI, а не общие типы
([ADR-002](docs/ADR/ADR-002-openapi-contract.md)).

## Карта

- [AGENTS.md](AGENTS.md) — точка входа для агентов: что читать перед задачей, команды,
  когда работа готова. `CLAUDE.md` подключает его.

### Общее — [`docs/`](docs/)

- [ADR](docs/ADR/README.md) — как фиксировать значимые архитектурные и продуктовые
  решения; [ADR-001](docs/ADR/ADR-001-decisions-as-adr.md) — само решение их фиксировать.
- [Glossary](docs/Glossary.md) — шаблон: утверждённые термины интерфейса на всех языках.
- [Backlog](docs/Backlog.md) — решённое, но отложенное, пока нет трекера.

### API — [`apps/api/docs/`](apps/api/docs/README.md)

Слои и прагматичный DDD, DI, ошибки, именование, тесты, фоновые задачи, схема данных; шаблоны
архитектуры, конфигурации, деплоя и доступа к данным; профиль платформы.

### Каркас — [`scaffold/`](scaffold/) (удаляется при инициализации)

- [INIT.md](scaffold/INIT.md) — инструкция агенту по инициализации.
- [Профили платформы](scaffold/profiles/README.md) — Cloudflare Workers + D1, Node.js +
  PostgreSQL; как написать новый.

### Веб-клиент — [`apps/web/docs/`](apps/web/docs/README.md)

Шаблон дизайн-документа: токены и правила интерфейса.
