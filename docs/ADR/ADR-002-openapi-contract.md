# ADR-002: Контракт между приложениями — спецификация OpenAPI

## Status
Accepted

## Context

api и его клиенты (веб-клиент, воркеры, внешние интеграции) живут в одном репозитории,
и проще всего связать их общим пакетом с типами, вплоть до типов, которые генерирует
ORM. Тогда схема базы становится публичным контрактом: переименование колонки ломает
клиента, внутреннее поле утекает в ответ, а клиент не отличает, что api обещает, от
того, как api устроен внутри.

## Decision

1. Контракт между api и любым клиентом — спецификация OpenAPI, которую api собирает из
   своих схем валидации запросов и ответов.
2. Спецификация — производный артефакт: она не правится руками, контракт меняется
   правкой схем в api.
3. Приложения не делят типы базы данных и ORM. Типы клиента генерируются из
   спецификации или пишутся по ней.
4. Ответ api описан схемой явно: сущность из базы не отдаётся как есть.

## Rationale

- **Схема БД и контракт меняются по разным причинам.** Разделение позволяет менять
  хранение, не трогая клиентов, и видеть изменение контракта в diff схем api.
- **Один источник истины.** Одни и те же схемы валидируют запрос, описывают ответ и
  порождают документацию; спецификация не расходится с кодом, потому что не пишется
  отдельно.
- **Контракт не привязан к языку.** OpenAPI читают клиенты на любом стеке и внешние
  интеграции.
- Рассматривали: общий пакет с типами, включая типы ORM (утечка схемы БД, см.
  Context); RPC-библиотеки со сквозной типизацией между TypeScript-приложениями (типы
  без генерации, но контракт существует только для TypeScript-клиентов, нет
  описания для внешних интеграций, а клиенты привязаны к библиотеке).

## Consequences and Risks

- Генерация типов клиента — шаг сборки, а схемы ответов пишутся явно даже там, где
  проще было бы вернуть сущность.
- Риск — хендлер возвращает не то, что описано в схеме ответа. Тесты контракта API
  проверяют ответ по схеме.
