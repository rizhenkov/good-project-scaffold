# Сборка зависимостей (DI)

Зависимости собираются в одном месте, composition root: `src/config/container.ts`. По
умолчанию — вручную, без библиотеки: функция создаёт объекты через `new` и возвращает
типизированный объект.

## Зачем

Application-слой зависит от **портов** (интерфейсов), а не от ORM, хранилища или
платёжки. Это даёт тестируемость (юнит-тесты собирают сервис руками на фейках,
интеграционные подменяют внешние порты через `createContainer(config, overrides)`) и
возможность заменить провайдера, не трогая бизнес-логику: две реализации
(`S3FileStorage`, `LocalFileStorage`) стоят за одним портом `FileStorage`, выбор —
переменная конфигурации и одно ветвление в `container.ts`.

## Выбор инструмента

- **Ручная сборка — вариант по умолчанию.** Компилятор проверяет, что каждому
  конструктору передано то, что он ждёт; нет декораторов, `reflect-metadata` и
  зависимости от сборщика; работает в любом рантайме.
- **DI-библиотека** (проверенный вариант — tsyringe) — когда граф большой: десятки
  сервисов, и порядок ручной сборки стал заметной работой. Цена — строковые токены,
  которые компилятор не сверяет с типами, и legacy-декораторы TypeScript. Правила —
  раздел «Если выбран tsyringe».
- **Если у фреймворка есть свой DI**, сначала рассматривается он, при двух условиях:
  domain и application не импортируют фреймворк
  ([Layer-Boundaries](Conventions/Layer-Boundaries.md)), и DI работает в сборщике
  проекта. Например, DI NestJS опирается на `emitDecoratorMetadata`, которого esbuild
  не эмитит.

Выбор фиксируется в ADR.

## Ручная сборка

```typescript
// config/container.ts
export interface Container {
    cancelOrder: CancelOrderService;
    uploadFile: UploadFileService;
}

/** Порты к внешнему миру, которые тесты вправе подменить. */
export interface Overrides {
    fileStorage?: FileStorage;
    emailSender?: EmailSender;
}

export function createContainer(config: AppConfig, overrides: Overrides = {}): Container {
    const db = createDbClient(config.database);
    const orders = new PrismaOrderRepository(db);
    const files =
        overrides.fileStorage ??
        (config.fileStorage === 's3'
            ? new S3FileStorage(config.s3)
            : new LocalFileStorage(config.localStoragePath));

    return {
        cancelOrder: new CancelOrderService(orders),
        uploadFile: new UploadFileService(files),
    };
}
```

- В `Container` попадают только то, что берёт presentation и точки входа (сервисы), и
  клиенты, которые нужно закрыть. Репозитории и адаптеры остаются локальными
  переменными функции.
- `Overrides` перечисляет порты к внешнему миру и больше ничего: репозитории и
  сервисы в тестах настоящие.
- Сервис, который нужен не каждому событию и дорог в сборке, отдаётся геттером или
  фабрикой, чтобы не собираться зря.

## Жизненный цикл

`createContainer(config, overrides?)` валидирует конфигурацию и собирает граф;
глобальных экземпляров нет.

Когда собирается контейнер (один раз на процесс или на каждое событие) и когда
закрываются клиенты, задаёт платформа: [Platform.md](Platform.md), «Время жизни
контейнера». В любом варианте контейнер запроса живёт в контексте запроса, а не в
глобальной переменной. То, что живёт один запрос (текущий пользователь, request id),
передаётся аргументом в метод сервиса.

В тестах легальные швы — только порты к внешнему миру, через `overrides`; без
override порты собираются из конфигурации, как в production. Какие порты подменяются и
какими фейками, и smoke-тест, который собирает контейнер без overrides, —
[Test-Setup.md](Test-Setup.md).

Таблица портов, которые собирает `createContainer`, ведётся здесь же: порт и что под
ним (реализация, при выборе — какая переменная выбирает).

| Порт | Реализация | Чем выбирается |
|------|------------|----------------|

## Правила

- Домен о сборке не знает; application-сервисы — обычные классы, зависимости приходят
  через конструктор.
- В presentation сервис берётся внутри хендлера из контейнера запроса. Глобального
  контейнера, который роут мог бы импортировать, нет.
- Типы и клиенты платформы создаются в `config` и передаются в реализации через
  конструкторы. Где их разрешено импортировать —
  [Layer-Boundaries](Conventions/Layer-Boundaries.md), «Config».

## Если выбран tsyringe

Раздел удаляется при инициализации, если DI-библиотека не выбрана.

### Токены

Интерфейсы TypeScript стираются при компиляции, поэтому инъекция по контракту идёт
через строковые токены:

```typescript
// application/services/cancel-order.service.ts
@injectable()
export class CancelOrderService {
    constructor(@inject('OrderRepository') private readonly orders: OrderRepository) {}
}

// config/container.ts
container.registerSingleton('OrderRepository', PrismaOrderRepository);
container.registerSingleton('CancelOrderService', CancelOrderService);
```

Токен совпадает с именем интерфейса (`'OrderRepository'` ↔ `interface OrderRepository`,
[Naming](Conventions/Naming.md)). Компилятор строку токена с типом параметра не
сверяет: `@inject('FileStorage') orders: OrderRepository` скомпилируется и упадёт
только при вызове метода. Smoke-тест этого не ловит (токен резолвится), ловят
интеграционные тесты, которые проходят через сервис, и ревью по правилу имени.

### `@inject` обязателен на каждом параметре конструктора

Многие сборщики (esbuild и всё, что на нём построено) не поддерживают
`emitDecoratorMetadata`. Без метаданных `design:paramtypes` tsyringe не может
угадать зависимость по типу параметра, и класс с хотя бы одним параметром без `@inject`
упадёт при первом `resolve` в собранном приложении. Локальный запуск через рантайм,
который метаданные эмитит, разницы не покажет; тесты в том же сборщике и рантайме, что
и production, покажут.

Правило: **каждый параметр конструктора в `@injectable()`-классе помечен `@inject('Token')`**,
включая зависимости классового типа. `emitDecoratorMetadata` в `tsconfig.json`
выключен, чтобы локально не было ложной уверенности.

### Контейнер

`createContainer` регистрирует всё в **дочернем** контейнере tsyringe и возвращает его;
глобально ничего не регистрируется. Таблица выше ведётся по токенам.

Реализации без декораторов (адаптеры SDK, хэшеры с параметрами) собираются в
`container.ts` через `new` и регистрируются `registerInstance`: их параметры —
конфигурация и клиенты, а не другие токены.

| Метод               | Что делает                           | Когда                                             |
|---------------------|--------------------------------------|---------------------------------------------------|
| `register`          | Новый экземпляр при каждом `resolve` | Stateless-классы с состоянием на один запрос      |
| `registerSingleton` | Один экземпляр на контейнер          | Сервисы, репозитории (почти всё)                  |
| `registerInstance`  | Регистрирует уже созданный объект    | `AppConfig`, подключения, клиент ORM, клиенты SDK |

### Декораторы

- `@injectable()` / `@inject()` — только в `application` и `infrastructure`.
- Декораторы импортируются из своего модуля (`@/shared/di.ts`), а не из `tsyringe`
  напрямую. Этот модуль первым делом подгружает `reflect-metadata`, поэтому порядок
  соблюдается в любой точке входа, включая unit-тест, который собирает класс руками
  без контейнера. `tsconfig.json` включает `experimentalDecorators`, линтер —
  поддержку декораторов параметров.
