# Тесты (Test Placement)

| Вид             | Где                                 | Что проверяет                                                                     |
|:----------------|:------------------------------------|:----------------------------------------------------------------------------------|
| **Unit**        | рядом с кодом, `src/`               | Один класс или функция в изоляции, на фейках                                      |
| **Integration** | `tests/integration/`                | Сценарии через границы модулей: БД с миграциями, хранилище, очереди, запрос через приложение |
| **Contract**    | `tests/contracts/` (когда появятся) | Живой внешний API всё ещё отвечает так, как мы ожидаем                            |

Оба первых вида гоняет один раннер, в том же рантайме, что и production. Разница между
ними не в раннере, а в том, трогает ли тест БД, хранилище и другую инфраструктуру.

## Unit — рядом с кодом

`<имя>.test.ts` в той же папке, что и `<имя>.ts`.

```
src/domain/entities/
  order.entity.ts
  order.entity.test.ts
```

Открыл папку — видно, что покрыто. Переименовал модуль — тест переехал с ним.
Unit-тест не трогает БД, хранилище, очереди и сеть. Нужна инфраструктура — это integration.

### Фейки вместо контейнера

Application-сервис — обычный класс, его можно собрать руками с in-memory реализациями
портов, без `createContainer` (см. [../DI-Container.md](../DI-Container.md)):

```typescript
const orders = new InMemoryOrderRepository();
const service = new CancelOrderService(orders);
```

Общие фейки лежат рядом с сервисами (`*.test-support.ts`). Фейк держит состояние и
отвергает то же, что отвергла бы настоящая система (например, фейковая платёжка не
находит платёж, который не создавали, и не возвращает больше, чем было оплачено).
Тест через фейк читает результат (отправленные письма) или задаёт ответ (лимитер
отказывает).

Подменяется только то, что зовёт тестируемый модуль. Если для теста нужно больше
нескольких фейков, рефакторинга требует модуль, а не тест.

## Integration — `tests/integration/`

Работают с локальной БД (миграции применены в setup) и локальным или фейковым
хранилищем. Контракт API — запросом к приложению, собранному тестовой фабрикой
(`createTestApp()`): настоящие роуты, сервисы, репозитории и БД, а порты к внешнему
миру (хранилище, почта, лимитер, платёжка) подменены через `overrides`
([../DI-Container.md](../DI-Container.md)). Тест играет клиента: входит тем же путём,
что пользователь (например, берёт код или ссылку из письма в фейковом почтовом ящике),
а не подделывает токен; вызывает API, проверяет ответ и состояние.
Сторонние API здесь **мокаются**: проверяем нашу реакцию на ответ, а не доступность
чужого сервиса.

## Contract — `tests/contracts/`

Реальные вызовы к внешним API (платёжка, настоящее хранилище). Не входят в обычный
прогон: гоняются вручную или по расписанию, self-skip, если нет нужных переменных
окружения.

## Герметичность

Обычный прогон не зависит от машины разработчика и ничего не трогает за её пределами:

- **Конфигурация.** Тестовые значения всех переменных заданы в конфиге тестов.
  Env-файлы разработчика не читаются. Отдельный тест сверяет список переменных
  приложения со списком тестовых: production-значение не должно приходить в тесты
  молча.
- **Сети нет.** Исходящий запрос из кода под тестом блокируется и падает с понятной
  ошибкой. Нужно поведение внешнего API — подмена на уровне порта или внедрённый
  `fetch`.
- **Данные разработчика не трогаются.** Тесты работают со своей одноразовой БД, а не с
  локальной базой, на которой разработчик запускает приложение.
- **Без sleep и ожиданий по времени.** «Просроченность» задаётся данными (`createdAt`
  в прошлом), окна и кулдауны — сдвигом записей в прошлое, а не ожиданием.
- **Дорогие параметры уменьшены.** Хэширование паролей и подобное — тот же алгоритм на
  малых параметрах, иначе прогон тратит секунды на вычисления.

Как это устроено в проекте (setup, изоляция между тестами, сиды) — [Test-Setup.md](../Test-Setup.md).
