# Фоновые задачи (очереди и расписания)

Правила, которые код о себе не рассказывает: формат сообщений, идемпотентность, выбор
между очередью и расписанием, что проверять в тестах. Топология очередей, повторы и
расписания живут в конфигурации платформы; схема сообщений — в
`infrastructure/queue/messages.schema.ts`.
Как платформа доставляет, повторяет и запускает — [Platform.md](../Platform.md),
«Очереди» и «Расписания».

## 1. Очередь или расписание

| Нужно                                                                                    | Инструмент                                       |
|:-----------------------------------------------------------------------------------------|:-------------------------------------------------|
| Сделать что-то в ответ на действие пользователя, но не в HTTP-запросе (письмо, пересчёт) | сообщение в очередь через порт `JobQueue`        |
| Регулярно пройти по данным (чистка брошенного, выборка записей по сроку)                 | расписание (cron), свой application-сервис       |
| Сделать что-то в точный момент времени для одной сущности                                | отдельное решение, когда понадобится             |

Эндпоинтов «дёрни меня по крону» нет.

Если состояние должен писать ровно один писатель (например, остаток товара на складе), у него своя
очередь с конкурентностью 1 и свой порт. Схемы у очередей разные, поэтому задание
единственного писателя нельзя по ошибке отправить в параллельную очередь: её
консьюмер такое сообщение не разберёт.

### Запись в БД и постановка задачи

Use case, который меняет данные и ставит задачу, пишет в две системы, и падение между
записями теряет задачу. Задание защищает повтор входящего сообщения (§3, «Задания
единственного писателя»), а у HTTP-запроса повтора нет. Поэтому use case, вызванный не
из очереди, делает одну атомарную запись:

- результат нужен в ответе → пишет в БД и в той же записи фиксирует, что задача
  нужна: статус, который подбирает расписание (`refundStatus = PENDING`), или строку
  outbox, которую ретранслятор ставит в очередь;
- результат в ответе не нужен → только ставит задачу, запись делает она;
- очередь живёт в той же БД и задача ставится в той же транзакции → это одна запись,
  правило выполнено. Есть ли такая очередь — [Platform.md](../Platform.md), «Очереди».

## 2. Сообщения

- Сообщение — JSON с полем `type` (`camelCase`, например `cancelUnpaidOrder`) и
  `payload` из доменных идентификаторов. Никаких готовых сущностей внутри: консьюмер
  перечитывает состояние из БД, потому что к моменту обработки оно могло измениться.
- Сборка сообщения живёт в реализации продюсера в `infrastructure`. Вызывающий код
  передаёт доменные части через порт `JobQueue`, порт про формат не знает.
- **Только идентификаторы, ничего персонального.** Сообщения лежат в очереди и в
  dead-letter сутками, а юрисдикция и сроки хранения очереди обычно не те, что у
  основной БД. Почта, имена, адреса, IP в `payload` не попадают — консьюмер возьмёт их
  из БД.
- Типы сообщений перечислены в одном месте как discriminated union, своя схема на
  очередь; консьюмер выбирает схему по очереди, сопоставляет `type` с
  application-сервисом и ничего больше не решает. Продюсер собирает сообщение типом,
  выведенным из схемы, поэтому расхождение со схемой — ошибка компиляции.
- Схемы лежат в `infrastructure`, а не в `config`: продюсерам импорт `config` запрещён
  ([Layer-Boundaries.md](Layer-Boundaries.md), «Infrastructure»), а `config` и точки
  входа импортируют `infrastructure` свободно.

## 3. Идемпотентность и «не более одного в полёте»

Очередь гарантирует at-least-once: сообщение может прийти дважды, а два запуска по
расписанию могут наложиться, если предыдущий не уложился в интервал. Защита живёт в
данных, не в очереди:

- **Повтор безопасен по состоянию.** Хендлер сначала читает текущее состояние и выходит,
  если работа уже сделана (запись уже `DELETED`, заказ уже отменён). Удаление
  объекта, которого нет, не ошибка.
- **Захват через условный `UPDATE`.** Когда работа не идемпотентна сама по себе,
  хендлер переводит запись в промежуточный статус одним `UPDATE ... WHERE status = ?`
  и продолжает только если изменилась ровно одна строка. Второй запуск увидит ноль
  строк и выйдет.
- **Детерминированные ключи** там, где нужен след выполнения: таблица с уникальным
  ключом операции (`<type>_<entityId>_<period>`), вставка в неё — первый шаг хендлера.
- **Ключ идемпотентности — статус.** Переход применяется только из ожидаемого статуса
  (`PENDING → SUCCEEDED`, откат только из `SUCCEEDED`), повтор ничего не меняет.

### Задания единственного писателя

- Читают, решают и пишут одной атомарной записью. Решают по состоянию на момент
  выполнения, а не постановки: проход по сроку выбрал запись час назад, а её
  могли оплатить.
- Не ходят во внешние системы. Медленное и внешнее (возврат платежа, письмо
  покупателю) ставится после записи задачей в параллельную очередь. Задание, пришедшее повторно,
  видит свою работу сделанной и ставит такую задачу ещё раз: процесс мог упасть между
  записью и постановкой.
- Порядок шагов между БД и внешней системой выбирается так, чтобы падение между ними
  не оставило запись, которая ссылается на несуществующее. Например, фото товара:
  сначала файл в хранилище, потом строка о нём. Лишний файл без строки подберёт
  фоновая чистка, а строку без файла покупатель увидит битой картинкой.
- Если вход задания велик или его результат нужно показать пользователю, сообщение
  несёт только id строки задания: вход и результат лежат в строке, строка же — ключ
  идемпотентности. Результат пишется в той же записи, что и само изменение; доменная
  ошибка закрывает строку `FAILED` с кодом.

## 4. Повторы и dead-letter

- По умолчанию at-least-once: ограниченное число повторов с растущей задержкой, после
  исчерпания сообщение уходит в dead-letter очередь. Dead-letter обязательна у каждой
  очереди: потерянное молча сообщение хуже упавшего.
- Хендлер подтверждает сообщение (`ack`) только после успешного завершения; исключение
  приводит к повтору. Если консьюмер получает пачку, каждое сообщение подтверждается
  или повторяется отдельно, чтобы одно плохое сообщение не тянуло за собой остальные.
- At-most-once (без повторов) только если повтор продублирует уже совершённый
  побочный эффект, и причина пишется комментарием рядом с настройкой очереди.
- Доменная ошибка (`DomainError`, например записи нет) подтверждает сообщение и пишется
  в лог: повтор встретит то же состояние. Исключение — `ConcurrencyError`: состояние
  изменилось между чтением и записью, повтор перечитает его и решит заново
  ([Database.md](Database.md) §5). Повторяется и всё остальное: сбой БД или
  хранилища, сообщение, которое не разбирается схемой, неизвестная очередь.
- Отложить работу, которая не сбой, а ожидание (дневная квота API службы доставки
  исчерпана, а задание нельзя потерять), — новое сообщение с задержкой через порт, а
  текущее подтвердить.
  Не повтор: повторы расходуют лимит попыток и уводят сообщение в dead-letter.
- Чем дороже потеря задания (деньги), тем больше повторов у его очереди.

## 5. Расписания

- Каждый запуск обрабатывает ограниченную пачку по индексу (`status`, `createdAt`,
  срок) и завершается; остаток дождётся следующего тика. Так запуск укладывается в
  лимиты времени, а полных сканов нет (см. [Database.md](Database.md)).
- У каждого расписания свой application-сервис. Выражения — константы в одном конфиге;
  если платформа объявляет расписания ещё и в своей конфигурации, тест сверяет их.
- Расписание запускается один раз на все экземпляры приложения, а не в каждом. Как
  это обеспечивает платформа — [Platform.md](../Platform.md), «Расписания».
- Интервал растягивается, если пачка не успевает: для housekeeping это допустимо,
  для чего-то срочного учитывать.

## 6. Тесты

- Хендлер задачи — обычный application-сервис, тестируется на фейках как любой другой.
- Продюсеры тестируются на фейковых очередях, которые подставляет тестовая фабрика
  приложения; поставленное задание тест выполняет сам, вызовом его сервиса. В настоящую
  локальную очередь тесты не пишут: сообщение дошло бы до консьюмера в
  непредсказуемый момент.
- Последовательность заданий единственного писателя тестом не проверяется: её задаёт
  конфигурация очереди.
- Консьюмер тестируется прямым вызовом точки входа с собранной пачкой сообщений:
  проверяется, какие сообщения получили `ack`, какие `retry` и с какой задержкой.
  Расписания — прямым вызовом точки входа расписания.
- Без sleep — [Testing.md](Testing.md#герметичность).
