# Схема данных

Правила для схемы, которая должна оставаться дешёвой и быстрой при росте данных.
Насколько они строги на конкретной БД (например, там, где платят за прочитанные
строки) и чем проверяются — [Platform.md](../Platform.md), «База данных».

## 1. Запросы к растущим таблицам идут по индексу

Без индекса `SELECT ... WHERE status = ?` читает всю таблицу, сколько бы строк ни
вернул.

- У каждого пути чтения таблицы, которая растёт вместе с пользователями или временем,
  есть индекс, составной, если фильтр составной (`[status, createdAt]`,
  `[customerId, dueAt]`).
- Полный скан такой таблицы на пути запроса — ошибка проектирования, а не медленный
  запрос. Если запрос не ложится ни на один индекс, меняется схема, а не принимается
  цена. Маленькие справочники и редкие внутренние выборки под правило не попадают.
- Индекс для нового пути назван в ревью (§7). Проверяется ли план автоматически —
  [Platform.md](../Platform.md), «База данных».

## 2. Агрегаты: считать или хранить

`COUNT(*)` и `SUM` по таблице читают все строки, которые считают. По умолчанию агрегат
считается запросом по индексу; хранится полем, если выполняется одно из условий:

- по нему проверяется правило при конкурентной записи (лимит заказов, остаток): посчитать
  и затем записать — гонка;
- он нужен на горячем пути и считается по растущему набору строк;
- платформа делает чтение строк дорогим ([Platform.md](../Platform.md), «База данных»).

Хранимый агрегат обновляется в той же записи, что и событие. Если агрегат нужен редко
и для внутренних целей, его считает фоновая задача пачками, а не запрос в HTTP.

- Когда агрегат меняют записи из разных мест, изменение выводится в SQL из самой
  строки в той же транзакции, перед оператором, который её меняет:
  `величина × (будет считаться − считается сейчас)`, где «считается» — 1 или 0 по
  статусу. Например, сумма открытых заказов клиента при отмене заказа меняется на
  `amount × (0 − 1)`, а при повторной отмене уже отменённого — на `amount × (0 − 0)`.
  Тогда повтор записи ничего не добавляет, а две копии одного перехода добавляют один
  раз. Запись, условная на статус, ставит то же условие и счётчику: не изменила
  строку — не изменила и его.

## 3. Списки — курсорная пагинация с жёстким лимитом

- `OFFSET` читает и отбрасывает пропущенные строки. Списки идут по курсору
  (`WHERE (createdAt, id) < (?, ?) ORDER BY createdAt DESC, id DESC LIMIT ?`), курсор —
  значения последней строки, не номер страницы.
- У каждого списка есть верхний предел лимита в коде; «отдать всё» не бывает.
- Фоновые проходы работают по той же схеме: пачка по индексу, остаток — следующему тику.

## 4. Лимиты, которые влияют на схему

Лимиты конкретной БД (размер базы и строки, число колонок и параметров запроса,
длительность запроса, число писателей и подключений) выписаны таблицей с колонкой
«следствие» в [Platform.md](../Platform.md), «База данных». Типичные следствия:

- в БД — метаданные, не содержимое: никаких blob'ов и логов, большие структуры — в
  объектное хранилище;
- JSON-поля короткие;
- колонки «на всякий случай» не копятся;
- `IN (...)` по id режется на пачки в репозитории;
- длинные операции — пачками;
- транзакции короткие, без ожидания внешних вызовов внутри.

## 5. Транзакции

Внутри транзакции нет внешних вызовов (хранилище, очередь, HTTP): она короткая и не
ждёт чужих систем. Как запись сочетается с задачей в очереди —
[Background-Jobs.md](Background-Jobs.md) §1, «Запись в БД и постановка задачи».

Чтение, по результату которого решается запись, защищено от параллельного изменения.
Есть ли интерактивные транзакции и блокировки строк и каким механизмом делается
атомарная запись нескольких строк — [Platform.md](../Platform.md), «Атомарность».

### Условное сохранение агрегата

Типовой use case читает агрегат, вызывает его метод и сохраняет:
`findById` → `order.cancel()` → `save(order)`. Между чтением и записью агрегат мог
изменить другой запрос, поэтому:

- `save()` пишет условно: `UPDATE … WHERE id = ? AND version = ?` с версией на момент
  загрузки и увеличивает `version`. Колонка `version` есть у корня каждого агрегата,
  который меняется после создания. Условие по статусу на момент загрузки вместо версии
  допустимо, только если агрегат меняется исключительно переходами статуса.
- Условие проверяет, что агрегат не изменился с момента чтения, а не бизнес-правило.
  Правило («отменить можно только неотправленный заказ») остаётся в домене; в `WHERE`
  не пишется `status != 'SHIPPED'`.
- Изменилось ноль строк — репозиторий бросает `ConcurrencyError`
  ([Errors.md](Errors.md), `CONCURRENT_MODIFICATION`, `409`). Сервис сам не повторяет:
  решение принималось по устаревшему состоянию. Клиент HTTP перечитывает ресурс; в
  фоновой задаче повтор делает очередь ([Background-Jobs.md](Background-Jobs.md) §4).
- Дочерние строки агрегата пишутся той же атомарной записью, что и корень, и только
  если условие корня выполнено. Как это обеспечить на платформе —
  [Platform.md](../Platform.md), «Атомарность».
- Блокировка строки (`SELECT … FOR UPDATE`) — не способ по умолчанию: ей нужна
  транзакция от чтения до записи, то есть Unit of Work на весь use case. Её берут, когда
  конфликты частые и повтор дорог, и только если платформа её даёт.
- У каждого репозитория с `save()` есть тест: два чтения одного агрегата, два
  сохранения, второе бросает `ConcurrencyError` и не оставляет следов.

Атомарность, которую обещает ORM, проверяется тестом, а не принимается на веру:
запись, которая падает на последнем операторе, не должна оставить следов первых.
Известные случаи, когда ORM этого не обеспечивает, и чем их обходить —
[Platform.md](../Platform.md), «Атомарность».

## 6. Типы и значения

- Идентификаторы — UUID v7. Они монотонны по времени, поэтому индекс по id даёт
  порядок создания бесплатно.
- Короткий публичный id (например, номер заказа, который видит покупатель) — отдельное решение. Его уникальность
  держит ограничение в БД; вставка — `create`, а не `upsert` (`upsert` молча перезапишет
  чужую запись), при конфликте — повтор с новым id. Такой id не монотонен, поэтому
  порядок создания берётся из `created_at`.
- Время — тип даты ORM; в сырых запросах используется то же представление, а не своё.
- Деньги и длительности — целые (центы, секунды), не числа с плавающей точкой.
- Статусы — значения из закрытого списка, который проверяет домен. Как список
  хранится в БД (`enum`, `CHECK`, строка) — [Platform.md](../Platform.md), «База данных».
- Возможности конкретной СУБД (частичные индексы, `CHECK`, JSON-типы) используются,
  когда дают выигрыш. Знает о них только инфраструктура: домен и application от СУБД
  не зависят ([Layer-Boundaries.md](Layer-Boundaries.md)).

## 7. Что проверять в ревью схемы

- Для каждого нового запроса в репозитории назван индекс, по которому он идёт.
- Новое хранимое поле-агрегат обновляется в той же операции, что и событие, и покрыто
  тестом на повтор.
- Новый список имеет курсор и предел лимита.
- `save()` нового агрегата условный и покрыт тестом на конкурентное сохранение (§5).
- Сгенерированная миграция прочитана целиком, а не только применена.

## 8. Миграции, которые удаляют или пересоздают данные

Миграция, которая удаляет таблицу или колонку, пересоздаёт таблицу или переносит
данные, может пройти без ошибок и при этом потерять строки. Обычные проверки этого не
ловят: тесты применяют миграции к пустой базе, локальный прогон ошибки не даёт, а
проверка вручную на записи, созданной после миграции, не видит пропажи старых. Как
именно это случается на конкретной СУБД (например, пересборка таблицы в SQLite
каскадом уносит дочерние строки) — [Platform.md](../Platform.md), «Миграции».

Правила для такой миграции:

- Не принимать её в сгенерированном виде. Выписать, какие строки она затрагивает,
  включая дочерние по внешним ключам и что с ними делает их `onDelete`. Сохранить
  данные в той же миграции или обойтись без разрушающего шага. После правки генератор
  должен подтвердить, что схема совпадает с миграциями.
- Доказать постоянным интеграционным тестом: он сеет строки в затронутой и во всех
  дочерних таблицах, выполняет SQL миграции и проверяет, что все строки на месте. Тест
  остаётся в наборе, так что и перегенерированная позже миграция его не пройдёт.
  «Применилась без ошибок» не доказывает ничего.

## 9. Применённые миграции не редактируются

Миграцию, уже применённую где-либо, кроме локальной машины, не редактировать:
исправление — новой миграцией.
