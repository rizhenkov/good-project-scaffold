# Границы слоёв (Layer Boundaries)

Послойная (чистая) архитектура на тактических паттернах DDD, применяемых прагматично:
код говорит на языке предметной области (`Order`, `Customer`, `Payment`, а не
`DbRow` и `JsonPayload`), есть сущности с поведением и репозитории как интерфейсы,
но без стратегического деления на bounded contexts — это монолит с чётко выделенным ядром.

Главное правило — **Dependency Rule**: зависимости в исходном коде указывают только
внутрь. Домен ничего не знает о БД, HTTP и внешних API. Правило проверяется
автоматически линтером зависимостей в CI: правила —
[`.dependency-cruiser.cjs`](../../.dependency-cruiser.cjs). Исключения в конфиг ради
зелёной проверки не добавляются: исправляется направление зависимости.

```
presentation ──▶ application ──▶ domain
                     ▲               ▲
                     └── infrastructure (реализует порты)
shared ◀── все, кроме domain (shared ни от кого не зависит)
shared/utils ◀── все, включая domain (utils не зависят ни от чего)
config ──▶ все (composition root, исключение из правил)
```

## Слои

### Domain — `src/domain`

Ядро. Сущности (`Order`, `Customer`), value objects (`Money`, `Quantity`), бизнес-правила
(«отменить можно только ещё не отправленный заказ»), доменные ошибки,
**интерфейсы репозиториев**.

Чего здесь нет: ORM, HTTP-фреймворка, DI-контейнера и любых внешних библиотек. Из
`src/shared` домен берёт только `shared/utils`: чистые функции без зависимостей (два
правила линтера зависимостей: домен из `shared` видит только `utils`, а `utils` не
зависят ни от чего).

```typescript
// src/domain/entities/order.entity.ts
export class Order {
    cancel(): void {
        if (this.status === 'SHIPPED') {
            throw new OrderAlreadyShippedError(this.id);
        }
        this.status = 'CANCELLED';
    }
}
```

### Application — `src/application`

Дирижёр. Use cases (`services/`): принимают команду, вызывают домен, работают с
репозиториями и портами, не принимают бизнес-решений сами. Здесь же **порты внешних
сервисов** (`interfaces/`): `FileStorage`, `PaymentGateway` — домену незачем знать,
что система умеет ходить в S3 или платёжку.

Чего здесь нет: SQL, HTTP-статусов, деталей сети.

```typescript
// src/application/services/cancel-order.service.ts
export class CancelOrderService {
    constructor(private readonly orders: OrderRepository) {}

    async execute(orderId: string): Promise<void> {
        const order = await this.orders.findById(orderId);
        order.cancel(); // бизнес-логика — в домене
        await this.orders.save(order); // условная запись: Database.md §5
    }
}
```

### Infrastructure — `src/infrastructure`

Общение с внешним миром. Реализации репозиториев на ORM (`repositories/`), клиенты
внешних систем (`services/`): хранилище, платежи, почта. Сгенерированный клиент ORM —
`infrastructure/db/generated/` (git-ignored). ORM импортируется только в
`repositories/`, `db/` и в `config`, где собирается клиент; остальные слои видят
репозиторий через интерфейс и получают его через конструктор.

Чего здесь нет: бизнес-логики и импортов из `config`. Инфраструктура «тупая»:
сохранить, прочитать, отправить. Настройки адаптер получает своим типом параметров
(`S3Options`), а не `AppConfig`: собирает их из `AppConfig` composition root.

### Presentation — `src/presentation`

Вход для HTTP. Роуты, валидация запроса по схеме, описание для OpenAPI, middleware,
маппинг доменных ошибок в `ApiError` с HTTP-статусом.

Чего здесь нет: вызовов ORM, бизнес-логики. Роут валидирует, зовёт application-сервис,
формирует ответ.

### Shared — `src/shared`

Переиспользуемое и не привязанное к предметной области: `ApiError`, глобальный
обработчик ошибок, базовые типы и утилиты. Сгенерированный код ORM сюда не кладётся:
он — инфраструктура, а `shared` доступен всем слоям.

`shared/utils` — единственная часть `shared`, доступная домену. Туда кладётся только
код без зависимостей: ни от других слоёв, ни от остального `shared`, ни от
npm-пакетов. Например, генерация id и криптографические хелперы.

Чего здесь нет: логики конкретных сущностей, зависимостей от других слоёв.

### Config — `src/config`

Composition root: валидированная конфигурация окружения (`AppConfig`), подключения к
БД и хранилищу, контейнер, клиент ORM, расписания, проверки готовности. Единственное
место вместе с `infrastructure`, где можно импортировать SDK платформы, на которой
работает приложение (правило линтера зависимостей). Знает про всех, его не знает
никто, кроме presentation (resolve из контейнера) и точки входа.

## Частые кейсы

- **Где интерфейс?** Нужен домену (репозиторий, генератор id) → `domain`. Нужен только
  для оркестрации (хранилище, платёжка) → `application/interfaces`.
- **Транзакции БД.** Клиент ORM в application не импортируется. Атомарность — внутри
  метода репозитория или через Unit of Work, которым владеет инфраструктура. Защита от
  параллельного изменения — условный `save()` ([Database.md](Database.md) §5).
- **Аутентификация.** Домен знает про роли и статусы. Application проверяет и просит
  порт выдать токен. Infrastructure знает, что это JWT. Заменим JWT на сессии — домен
  и application не меняются.

## Чего здесь нет

Паттерны из книг по DDD, которые сюда не берутся. Каждый стоит чего-то на каждой
задаче, а выгоду даёт в системах другого масштаба. Без явного запрета их легко
добавить «по учебнику»; если один из них понадобился — это решение для ADR.

- **Bounded contexts и anti-corruption layers.** Один домен и один словарь
  ([Glossary](../../../../docs/Glossary.md)). Перевод моделей между контекстами
  удваивает типы и на каждой задаче ставит вопрос «чей это контекст». Домен вырос —
  делится на модули с запретом импорта чужих внутренностей линтером зависимостей.
- **Доменные события внутри процесса** (шина, подписчики на `save`). Прячут поток
  управления: по коду use case не видно, что произойдёт дальше. Следующий шаг
  use case вызывает явно; отложенный — сообщение в очередь через порт `JobQueue`
  ([Background-Jobs.md](Background-Jobs.md)).
- **CQRS** (отдельные модели и хранилища для чтения и записи). Чтение и запись идут
  через один репозиторий; списки — его методы с курсорной пагинацией
  ([Database.md](Database.md) §3).
- **Event sourcing.** В БД хранится текущее состояние; защита от параллельных
  изменений — условный `save()` ([Database.md](Database.md) §5).

## Чек-лист: куда положить новый код

| Что делает код                                                           | Слой             |
|:-------------------------------------------------------------------------|:-----------------|
| Чистая бизнес-логика: правила, статусы, инварианты сущностей             | `domain`         |
| Координирует: зовёт домен, сохраняет, дёргает порты, сам не решает       | `application`    |
| Реализует внешнюю зависимость: ORM, S3, платёжка, почта, JWT             | `infrastructure` |
| Обрабатывает HTTP: парсит, валидирует, отдаёт статус                     | `presentation`   |
| Чистая утилита без зависимостей, нужна и домену                          | `shared/utils`   |
| Нужно везде, кроме домена: ошибки API, базовые типы                      | `shared`         |
| Собирает всё вместе: env, контейнер, клиенты                             | `config`         |
