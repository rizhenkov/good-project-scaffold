# Ошибки

## Формат ответа

Любая ошибка API — JSON одной формы:

```json
{
    "success": false,
    "status": 404,
    "code": "ORDER_NOT_FOUND",
    "error": "Order abc123 not found",
    "details": { "orderId": "abc123" }
}
```

- `code` — машиночитаемый, стабильный, `UPPER_SNAKE_CASE`. Фронтенд ветвится по нему,
  не по тексту.
- `error` — человекочитаемое сообщение. Может меняться.
- `details` — опционально, структурированный контекст.

Собирает это один глобальный обработчик ошибок (`src/shared/errors/error.handler.ts`),
подключённый к приложению. Неизвестный путь — такой же JSON с `NOT_FOUND`.

В лог ошибка попадает с `code`, идентификаторами и стеком; почта, имена, адреса, IP,
токены и тела запросов в лог не пишутся.

## Кто за что отвечает

| Слой           | Что бросает                                       | Знает про HTTP |
|:---------------|:--------------------------------------------------|:---------------|
| domain         | Доменные ошибки (`OrderAlreadyShippedError`)      | нет            |
| application    | Пробрасывает доменные, бросает свои прикладные    | нет            |
| infrastructure | Технические (сеть, БД), по возможности обёрнутые  | нет            |
| presentation   | Маппит доменные/прикладные в `ApiError` со статусом | да           |

`ApiError` (`src/shared/errors/api-error.ts`) — единственный класс, несущий HTTP-статус.
Ниже presentation его не создают.

Инфраструктуре разрешено бросать доменные ошибки, когда внешняя система отвечает
отказом с предметным смыслом (например, реализация `PaymentGateway` — на неподписанное
уведомление). Маппинг в статус — как у остальных, в presentation.

## Доменные ошибки

Доменные и прикладные ошибки наследуют `DomainError` (`src/domain/errors/domain.error.ts`):
стабильный `code`, человекочитаемое сообщение, опциональные `details`. Один класс — один
файл с суффиксом `.error.ts`.

Соответствие `code → HTTP-статус` живёт в одном месте —
`src/presentation/errors/domain-error.handler.ts`. Обработчик вешается на роутер фичи
и перебрасывает доменную ошибку как `ApiError` глобальному обработчику. Код без записи
в таблице — ошибка программиста, он уйдёт как 500.

**`400` или `422`.** `400` — только запрос, не прошедший схему (`VALIDATION_ERROR`, см.
ниже): сломан синтаксис или форма данных. Запрос, который прошёл схему, но нарушает
правило домена (количество больше допустимого на позицию, скидка больше 100 %), —
`422`. Доменная ошибка не получает `400`, даже если проверяет то же, что и схема:
проверка в домене — страховка, и клиент различает «запрос сломан» и «запрос понятен,
но отвергнут». `413` и `415` говорят о теле самого HTTP-запроса, а не о данных, которые
в нём описаны.

Таблица кодов ведётся здесь же, по строке на код. Пример формы:

| Код                     | Статус | Когда                                                   |
|:------------------------|:------:|:--------------------------------------------------------|
| `ORDER_NOT_FOUND`       | 404    | Нет заказа с таким id                                   |
| `ORDER_ALREADY_SHIPPED` | 409    | Операция недопустима для отправленного заказа; `details.status` |
| `CONCURRENT_MODIFICATION` | 409  | Ресурс изменён другим запросом между чтением и записью  |
| `QUANTITY_OUT_OF_RANGE` | 422    | Количество вне допустимого диапазона; `details.min`, `details.max` |
| `UNAUTHENTICATED`       | 401    | Нет действующей сессии                                  |
| `ACCESS_DENIED`         | 403    | Нет прав на ресурс                                      |
| `TOO_MANY_REQUESTS`     | 429    | Сработал лимит запросов; `details.scope`, заголовок `Retry-After` |
| `SERVICE_BUSY`          | 503    | Сработал предохранитель; заголовок `Retry-After`         |

`409` — операция недопустима в текущем состоянии ресурса; `422` — запрос нарушает
правило независимо от состояния.

`CONCURRENT_MODIFICATION` несёт `ConcurrencyError` (`src/domain/errors/concurrency.error.ts`,
наследует `DomainError`). Её бросает репозиторий, когда условное сохранение не изменило
ни одной строки ([Database.md](Database.md) §5): это часть контракта интерфейса
репозитория, поэтому класс лежит в домене. Клиент перечитывает ресурс и решает заново,
а не повторяет тот же запрос вслепую.

`UNAUTHENTICATED` (401) бросает middleware аутентификации сразу как `ApiError`, без
доменной ошибки: нет сессии — нечего маппить. Ответ несёт `WWW-Authenticate: Bearer`.

## Заголовки ответа

`ApiError` может нести заголовки (`headers`), глобальный обработчик их ставит. Обработчик
доменных ошибок добавляет `Retry-After`, когда в `details` есть `retryAfterSeconds`;
CORS отдаёт этот заголовок наружу (`exposeHeaders`), иначе браузер его не покажет.

## Валидация

Невалидный запрос ловит валидатор схемы до хендлера. Хук валидации
(`src/presentation/errors/validation.hook.ts`) переводит провал в общий формат с кодом
`VALIDATION_ERROR` и статусом 400:

```json
{
    "success": false,
    "status": 400,
    "code": "VALIDATION_ERROR",
    "error": "Invalid request",
    "details": {
        "issues": [{ "path": "quantity", "message": "Must be greater than 0" }]
    }
}
```

`path` — путь к полю через точку, пустой для ошибки на корне тела.
